# العمل بدون إنترنت والمزامنة · Offline-first & sync (v1.4.0)

> القاعدة: **القراءة من الجهاز، والكتابة لا تضيع.** أي تعديل يُحفظ محليًا ويُرسل تلقائيًا عند عودة الاتصال، دون تكرار.

## 1. ما يعمل بدون إنترنت؟

| يعمل offline | يحتاج إنترنت | لماذا |
| --- | --- | --- |
| البحث وقاعدة الأدوية (18 جهازًا · 225 مونوغرافًا · 493 منتجًا · 500 صورة) | تحليل وصفة جديدة | التحليل يجري على الخادم بنموذج AI — لا نموذج داخل التطبيق |
| قراءة الوصفات المحفوظة وبياناتها | رفع صور الوصفات | الصورة تُرسل للخادم |
| **إضافة/تعديل/حذف أصناف الصيدلية** | الاعتماد النهائي للوصفة (صيدلي) | قرار بشري يُسجَّل على الخادم |
| **إرسال طلبات إضافة دواء** | المجتمع/الوظائف عند التحديث | بيانات مشتركة |
| الحساسيات المسجّلة (قراءة) | إضافة حساسية *جديدة* | تُحفظ على الحساب |

الصور **لا تُوضع في الطابور**: ملف الصورة لا يضمن بقاءه بعد إغلاق التطبيق، فنطلب اتصالًا بدل الإيهام بالحفظ.

## 2. الطابور (Outbox)

- التخزين: `localStorage` مفتاح `mda.outbox.v1` (JSON صغير فقط).
- كل عملية تحمل: `id`، `method`, `path`, `body`, `label`, `attempts`, `status`, `idempotencyKey`.
- الحالات: `pending` → `syncing` → (`done` تُحذف) · `failed` · `conflict`.
- الترتيب محفوظ (FIFO)، والحد الأقصى 200 عملية.
- الطابور يُفرَّغ عند تسجيل الخروج (يخصّ الحساب السابق).

### متى تُوضع العملية في الطابور؟
فقط عند **فشل النقل** (`NetworkError`/انقطاع). أي رد من الخادم (400/403/409/…) هو إجابة حقيقية: يُعرض للمستخدم ولا يُعاد إرساله أعمى.
- `408/429/5xx` → إعادة تلقائية حتى 6 محاولات.
- `409` → توقف وطلب قرار من المستخدم.

## 3. منع التكرار: Idempotency-Key

عميل غير متصل لا يعرف هل وصل الطلب قبل الانقطاع. لذلك:

```
X-Idempotency-Key: <uuid ثابت للعملية>
```

- الخادم يخزّن **أول استجابة** للمفتاح (7 أيام، لكل مستخدم) ويعيدها عند التكرار مع `X-Idempotent-Replay: 1`.
- الجدول `idempotency_keys` يحفظ الاستجابة فقط — لا جسم الطلب (لا نصوص مرضى).
- مسارات الكتابة الإضافية للمخزون تدعم `client_uuid`: نفس المعرّف من نفس المستخدم لا يُنشئ صنفًا ثانيًا.

## 4. حل التعارض (Optimistic concurrency)

- عمود `version` + `updated_at` في `pharmacy_items`.
- التعديل/الحذف يرسل `expected_updated_at` (من آخر تحميل). إن اختلف → **409** مع صف الخادم الحالي.
- المستخدم يختار:
  | الخيار | ماذا يحدث |
  | --- | --- |
  | **احتفظ بنسختي** | إعادة الإرسال مع `?force=1` (يستبدل نسخة الخادم) بمفتاح idempotency جديد |
  | **استخدم نسخة الخادم** | حذف العملية من الطابور وإعادة التحميل |
- تعديلات المخزون النسبية (±) لا تتعارض عمدًا: جهازان كلاهما «-1» يعني -2 فعليًا.

## 5. واجهة المستخدم

- **شارة دائمة** في الشريط العلوي: أخضر «متزامن» · كهرماني «N بانتظار» · أحمر «تعارض/فشل» · رمادي «بدون إنترنت».
- **صفحة «المزامنة والاتصال»** (`/sync`): قائمة العمليات مع الحالة والمحاولات، أزرار إعادة المحاولة/التجاهل، وحل التعارض، وشرح ما يعمل بدون إنترنت.
- فحص الوصول: `GET /api/health` كل 45 ثانية (الإنترنت ≠ الخادم يستجيب)، ومزامنة تلقائية كل 30 ثانية عند وجود عمل معلّق، وفورًا عند حدث `online`.

## 6. الاختبارات

```bash
npm run test:sync    # 22 تحققًا
```

تغطي:
- الخادم: إعادة تشغيل بنفس المفتاح لا تُنشئ صفًا ثانيًا · `client_uuid` يمنع التكرار · `409` عند `updated_at` قديم مع صف الخادم · `force=1` يتجاوز · `version` يزيد · حذف قديم يُرفض.
- العميل: الطابور يحفظ المفاتيح، العملية الناجحة تخرج، التعارض يبقى بانتظار القرار، فشل النقل يُبقيها `pending` ويوقف الدفعة، عودة الاتصال تُفرّغ الطابور، و`4xx` تُعلَّم `failed` لا `pending`.

## 7. حدود معلنة

- لا تُزامن الصور ولا المرفقات في الطابور (v1.5 ستنقلها إلى IndexedDB مع ضغط).
- لا مزامنة خلفية حقيقية عندما يكون التطبيق مغلقًا (Android WorkManager يحتاج كودًا أصليًا؛ حاليًا المزامنة عند فتح التطبيق/عودة الشبكة).
- لا حل تعارض تلقائي «ذكي»: القرار للمستخدم، وهذا مقصود في بيانات الصيدلية.
- الطابور في `localStorage` — مسح بيانات الموقع/التطبيق يمسحه. لا ندّعي أنه قاعدة بيانات دائمة.
